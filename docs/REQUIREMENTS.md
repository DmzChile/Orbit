# Orbit — 제품 및 실제 구현 요구사항

문서 버전: 1.0 · 기준일: 2026-10-25 (Asia/Seoul)  
대상 저장소: `DmzChile/Orbit` · AI 작업 진입점: [`../AGENTS.md`](../AGENTS.md)

> 저장소에서는 이 파일을 `docs/REQUIREMENTS.md`에 둔다. 구현의 제품 기준 문서이며, 코드가 존재한다는 이유만으로 요구사항을 완료 처리하지 않는다. 각 항목은 ID로 추적하고 실제 검증 증거를 남긴다.

## 1. 목표와 원래 요청

사용자가 Windows에서 실행하는 다용도 개인 유틸리티 앱을 만든다. 뉴스 기사, 캘린더와 일정, 사용자 커스텀 공간을 제공한다. 메뉴의 금융·학습 등 원하는 주제를 끌어 커스텀 섹션에 배치한다. 앱에서 작업 요청을 보내고, GitHub 저장소의 최신 내용을 가져와 GPT 기반 작업을 정기 실행하며, 변경 사항과 결과물을 앱에서 자동 수신하는 것이 최종 목표다. UI는 Apple에서 영감을 받은 디자인과 모션을 사용한다.

최초 요청의 “일단 UI만 설계” 단계는 디자인 단계의 범위였다. 이 문서는 이후 실제 제품 구현을 위한 요구사항이다. 프로토타입의 메모리상 일정, 가짜 시세, 예시 뉴스, 가짜 PR, 타이머 기반 실행을 실제 기능으로 오인하지 않는다.

### 1.1 근거와 우선순위

1. 사용자의 현재 명시적 지시 및 승인된 제품 변경.
2. 이 요구사항 문서와 기록된 결정.
3. Figma의 시각적 구성과 HTML 프로토타입의 상호작용.
4. 기존 구현. 잘못된 기존 동작은 정답으로 간주하지 않는다.

디자인 참조:

| 내 공간 | 보드 선택, 편집 모드, 위젯 이동·추가·삭제·크기 변경, 초기화·되돌리기, 격자 배치, 위젯 라이브러리 |

좌측 메뉴는 오늘→뉴스→캘린더→내 공간→자동화→결과함 순서로 둔다. 위젯 둘러보기, 연결 상태, 설정, 사용자 워크스페이스를 제공한다. Windows 창 최소화·최대화·닫기는 실제 OS 동작과 연결한다.

## 3. 제품 기능 요구사항

### 3.1 앱과 대시보드

| ID | 요구사항 및 검증 기준 |
|---|---|
| APP-01 | 지원 Windows 버전·CPU 아키텍처·최소 사양을 기술 결정으로 명시하고 실제 Windows 설치 환경에서 실행한다. 우선 Windows 11 x64를 검증 대상으로 제안하되 지원 범위는 결정 기록으로 확정한다. |

### 3.5 GitHub 연결과 요청 전달

‘pull’은 혼동 없이 구분한다. **fetch/pull**은 저장소 최신 코드 동기화이고, **Pull Request(PR)**는 작업 결과 변경 제안이다. 사용자 의도에 맞춰 둘 모두 지원한다.

| ID | 요구사항 및 검증 기준 |
|---|---|
| GH-01 | 공식적으로 지원되는 인증 경로를 선정해 연결·권한 확인·저장소 목록·브랜치 선택·연결 해제·토큰 만료/취소를 처리한다. 필요한 저장소와 작업에 대한 최소 권한을 사용한다. |
| GH-02 | 앱의 요청을 영속 작업 레코드와 선택 저장소의 추적 가능한 요청 레코드에 연결한다. Issue/요청 파일/지원 이벤트 중 전달 방식을 결정하고 사용자 원문·요청 ID·생성 시각·대상 브랜치·상태·요구사항 버전을 추적한다. |
| GH-03 | 실행 시작 시 기준 브랜치의 최신 커밋을 가져와 격리된 브랜치/작업 공간에서 작업한다. 시작 SHA, 출력 SHA, 브랜치, PR 번호를 기록한다. 사용자 작업 트리와 진행 중 변경을 덮어쓰지 않는다. |
| GH-04 | 기본 변경 반영은 작업 브랜치와 PR 생성이다. 기본 브랜치 직접 push·자동 merge는 별도 명시적 설정/권한 없이는 수행하지 않는다. PR의 제목·변경 요약·요청 ID·테스트 결과·산출물 링크를 기록한다. |
| GH-05 | 브랜치 보호·충돌·읽기 전용·저장소 없음·인증 만료·API 제한을 구별해 안내한다. 무변경 작업은 ‘변경 없음’으로 완료 가능하며 빈 PR을 억지로 생성하지 않는다. |
| GH-06 | webhook을 사용하면 서명·전달 ID·대상 계정/저장소를 검증한다. 대안 polling은 주기·backoff·ETag/커서·API 제한을 고려한다. 이벤트 중복과 순서 뒤바뀜을 처리한다. |

| AUTO-05 | OS 앱, 예약/오케스트레이터, GitHub 동기화, AI 실행기, 산출물 저장·수신을 분리한다. 클라이언트에 모델 호출용 운영 비밀키를 내장하지 않는다. 실행기가 실제 코드 수정·빌드·테스트를 할 수 있는 환경인지 검증한다. 단순 텍스트 생성만으로 개발 작업 완료를 선언하지 않는다. |

| AUTO-08 | 앱 종료·오프라인·절전·서버 재시작에도 예약 정의와 작업 결과가 소실되지 않는다. 상시 실행은 실제 cloud/worker가 필요하면 구성에 명시한다. 로컬 전용 실행은 PC가 꺼진 동안 실행 불가와 재개 후 놓친 실행의 skip/coalesce/catch-up 정책을 명시한다. |
| AUTO-09 | 중첩 예약의 skip/queue 정책, 장시간 작업 취소, 늦게 도착한 완료 이벤트, 중복 PR/중복 과금·재업로드 방지를 처리한다. 영구 실패는 자동 재시도를 멈추고 복구 행동을 제공한다. |
| AUTO-10 | AI 모델/실행 공급자·예산/토큰·실행 시간 제한을 설정 가능하게 하고 사용량을 기록한다. 구독 혜택과 API 과금의 관계는 선택한 실행 경로의 공식 조건으로 확인하며 임의로 무료/무제한이라 가정하지 않는다. |
| AUTO-11 | 실행 시작 시 저장소의 `AGENTS.md`와 그 안에서 지정한 `docs/REQUIREMENTS.md`를 읽는다. 새 요청이 장기 요구사항을 변경하면 변경 내용을 추적한다. 실패한 테스트와 미구현 부분을 결과 요약에 포함한다. |

| SHIP-02 | 개발 환경, 실행·빌드·테스트·패키징 명령, 환경 변수 예제(값 없는 형태), 로컬/서버 실행 요건을 문서화한다. 고객 데이터나 자격증명을 예제로 커밋하지 않는다. |

## 6. 기술 결정 및 구현 순서

현재 저장소는 이 문서 작성 시점에 비어 있었다. 특정 프레임워크·서버·공급자·CI가 이미 존재한다고 가정하지 않는다.

1. **P0 — 실행 가능성 결정:** Windows 기술 스택, 로컬/클라우드 경계, GitHub 인증·요청 레코드, 공식 GPT 예약 연동 가능 여부, 실행기·산출물 공급자, 비용·권한을 확인한다. `docs/decisions/`에 근거·트레이드오프·미해결 사항을 기록한다.
2. **P1 — 앱과 로컬 데이터:** Windows shell, 디자인 토큰·내비게이션, 일정 CRUD·반복·알림 기반, 위젯 편집·영속화·공유 보드 모델을 구현한다.
3. **P2 — 읽기 공급자:** 실제 뉴스·금융·GitHub 읽기 데이터, 캐시·빈 상태·오류·인증을 연결한다.
4. **P3 — 수동 작업 한 회차:** 실제 요청 저장→격리 동기화→AI 작업→검증→PR/산출물→자동 수신의 최소 수직 흐름을 완성한다.
5. **P4 — 반복 실행:** 검증된 GPT 예약 어댑터 또는 명시적으로 승인된 대안, queue·중복 방지·취소·재시도·복구·알림을 구현한다.
6. **P5 — 출시 검증:** Windows 설치·배율·접근성·모션·보안·복구·성능·다운로드를 검증하고 문서를 갱신한다.

위 순서는 사용자 필수 기능의 삭제를 뜻하지 않는다. 부분 릴리스는 미완료 ID와 외부 연결 제한을 명확히 표시한다.

## 7. 수용 시나리오와 완료 정의

| E2E-04 | GitHub 인증→대상 저장소/브랜치→실제 요청 전송→최신 커밋 동기화→AI 코드/문서 작업→검증→실제 PR→실제 PDF/소스 산출물 생성→앱 자동 수신/다운로드·체크섬 확인. |

완료는 요구사항 ID별로 `미구현 / 진행 중 / 검증됨 / 차단됨 / 명시적 보류`를 기록하고, 검증 환경·명령/수동 절차·증거와 연결했을 때 인정한다. 스크린샷만으로 데이터 저장이나 예약 연동 완료를 증명하지 않는다. **데모로 성공한 UI, 실제 수동 실행, 실제 정기 실행, GPT 예약 직접 연동의 검증 상태를 각각 구분한다.**

제품 요구 변경 시 이 문서와 관련 수용 기준을 같이 갱신한다. 문서의 목표를 조용히 낮춰 구현의 완료를 맞추지 않는다.
